# Internationalization (i18n) Architecture

## Overview

The internationalization (i18n) architecture for the Gridbox Development website is designed to provide a frictionless, highly performant, and type-safe localized experience. Rather than relying on heavy third-party libraries that bloat the client bundle, this implementation leverages Next.js native features to resolve, negotiate, and serve localized content at the edge.

The system is built upon three core pillars:

1. **Edge-Level Negotiation**: Intercepting requests before they hit the server to determine the optimal language based on explicit URL paths, persistent user preferences, or browser defaults.

2. **Type-Safe Dictionaries**: Enforcing strict structural consistency across all supported languages at compile-time, eliminating runtime translation errors.

3. **Zero-Bundle Overhead**: Utilizing dynamic imports and React Server Components to ensure clients only download the translation strings required for their specific language and current page.

## Core Modules and Rationale

### The Source of Truth: [Configuration](/src/config/i18n/constants.ts)

Configuration values must be centralized to prevent scattered _"magic strings"_ and **ensure consistency across routing, rendering, and state management**.

- **Supported Locales and Default Locale**: Defined as strict `ReadonlyArray` and specific union types. This creates a strongly-typed foundation that propagates through the entire application. If a new language is added, the type system will automatically flag all areas of the application that require updates.

- **Persistent Preference**: We define a standard cookie (`NEXT_LOCALE`) with a 1-year lifespan (`maxAge: 31536000`). Language preference is a deeply personal user setting. By persisting this across sessions for a full year, we ensure returning users are never jarringly served content in the wrong language, reducing bounce rates and improving brand perception.

### The Traffic Controller: [Edge Middleware](/src/proxy.ts)

The middleware acts as the gateway for the i18n system. Its primary responsibility is to evaluate incoming requests and route the user to the correct localized path while keeping their persistent state (cookies) synchronized.

#### The Locale Resolution Hierarchy

To guarantee the best user experience, the middleware follows a strict priority cascade when determining which language to serve:

1. **Explicit Intent (URL Path):** If the URL contains a locale, this is treated as the absolute source of truth. Users might be sharing links or manually switching languages.

2. **Historical Preference (Cookie):** If the URL lacks a locale, the system checks for `NEXT_LOCALE`. If the user has visited before and set a preference, we respect it.

3. **Browser Default (Header Negotiation):** If no cookie exists, the system parses the `Accept-Language` header using `@formatjs/intl-localematcher` and `negotiator`. This ensures a first-time visitor from New York gets English, while one from Santiago gets Spanish, automatically.

4. **System Default:** Fallback to the `DEFAULT_LOCALE` if all else fails.

#### State Synchronization Strategy

The middleware doesn't just redirect, it actively maintains state consistency:

- **`handleExistingLocalePath`:** If a user visits `/en/about` but their cookie says `es`, the system assumes they want to switch to English. It seamlessly lets the request pass but attaches an updated cookie to the response (`createSyncCookieResponse`).

- **`handleMissingLocalePath`:** If a user visits `/about`, the system resolves the preferred locale (via hierarchy steps 2-4) and issues a 307 Redirect to the localized URL, writing the cookie simultaneously.

> [!INFO]
> Handling this logic in middleware prevents flashing of unstyled/unlocalized content (FOUC), avoids redundant server-side renders, and ensures SEO integrity by forcing crawlers into canonical, localized URL structures.

### Dictionary Management and Type Safety: [Management](/src/config/i18n/index.ts)

Managing translation files in a growing enterprise application often leads to bloated memory usage and missing translation keys. This module solves both issues through asynchronous loading and strict TypeScript validation.

#### Dynamic Loading for Performance

Instead of importing a massive JSON object containing all languages and all pages, the `dictionaries` object maps namespaces to asynchronous importer functions (`() => import(...)`).

This implements aggressively granular Code Splitting. When a user visits the Spanish homepage, the server only reads and parses the `es/metadata.json` file. English strings are completely ignored, keeping memory usage low and response times fast.

#### Deduplication with React Cache

The `getDictionary` function is wrapped in React's `cache()`.

In the Next.js App Router, multiple Server Components on the same page might need the same translation dictionary. Wrapping the loader in `cache()` memoizes the request per server-render cycle. If 5 components request the `es/metadata` dictionary, the filesystem is only queried once.

#### Compile-Time Structural Enforcement

The architecture utilizes TypeScript's `satisfies` operator and the `InferDictionary` utility type.

Translation files are notoriously prone to human error. By using `satisfies Record<Language, Record<string, () => Promise<unknown>>>` and inferring the schema from the `DEFAULT_LOCALE`, the architecture guarantees that all supported languages must provide the exact same namespaces and return the exact same object shapes.

Developer tooling will immediately throw a build error if a translation file is missing or structured incorrectly, preventing runtime crashes.

## Developer Guidelines

When interacting with this architecture, developers should adhere to the following principles:

1. **Never import `.json` files directly:** Always use `await getDictionary(locale, namespace)` inside Server Components. This ensures you benefit from caching and type inference.

2. **Rely on inferred types:** Do not manually type dictionary returns. Let `InferDictionary<P>` provide exact autocomplete for your translation keys.

3. **Respect the Namespace pattern:** As the application grows, break translations down by domain or feature rather than creating a single monolithic file. Add the new namespace to the `dictionaries` object in `index.ts`.

### Next.js App Router Integration Guidelines

To maintain alignment between this middleware and the application layout:

1. **Directory Structure**: Place all localized pages inside `app/[lang]`. The dynamic parameter lang will receive the validated locale prefix passed down by the middleware.

2. **Fetching Translations in Server Components**: Call `getDictionary(lang, namespace)` directly inside React Server Components:

```ts
import { getDictionary, type InferDictionary } from '@/config/i18n';

export default async function HomePage({ params }: PageProps<'/[lang]'>): Promise<JSX.Element> {
    const { lang } = await params;

    const dict = (await getDictionary(lang as Language, 'home')) as InferDictionary<'home'>;

    return <h1>{dict?.title}</h1>
}
```

3. **Language Switch UI**: Client components should switch languages simply by navigating to the corresponding localized path. There is no need for client-side cookie manipulation, `handleExistingLocalePath` will automatically synchronize the cookie upon request execution.
